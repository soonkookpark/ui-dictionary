01

일괄 선택 모드 Bulk select

목록에서 여러 항목을 체크해 한꺼번에 삭제·이동 같은 작업을 하는 모드. 하나를 길게 누르거나 "선택" 버튼을 누르면 체크박스가 나타나고, 아래나 위에 "3개 선택됨" 작업 바가 뜹니다. 항목 하나를 여는 일반 보기와 다른 상태입니다.

언제 쓰나메일 정리, 사진 여러 장 삭제, 관리자 화면의 대량 상태 변경처럼 같은 작업을 여러 번 반복해야 할 때.

AI에게 이렇게목록에 일괄 선택 모드를 넣어서 체크한 개수를 하단 작업 바에 보여주고, 전체 선택과 선택 해제 버튼도 넣어줘

20년차 메모가장 위험한 건 "전체 선택"입니다. 화면에 보이는 20개만 고른 건지, 필터에 걸린 전체 3천 개를 고른 건지 문구로 분명히 하세요. 일괄 삭제는 바로 지우기보다 "실행 취소"를 주는 편이 안전하고, 선택 모드에서는 항목을 눌렀을 때 열리는 동작이 체크로 바뀐다는 걸 개발자와 맞춰야 합니다.

02

자동 저장 표시 Autosave indicator

저장 버튼 없이 입력하는 대로 저장되고 있음을 작은 글자로 알려주는 표시. "저장 중…"에서 "저장됨"으로 바뀌는 것이 기본입니다. 저장 버튼이 있는 폼과 달리 사용자가 저장을 신경 쓰지 않아도 되게 만드는 장치입니다.

언제 쓰나문서·메모·디자인 도구처럼 오래 쓰다가 날릴까 걱정되는 편집 화면.

AI에게 이렇게문서 편집기에 자동 저장을 넣고, 상단에 저장 중, 저장됨, 저장 실패 상태 표시를 보여주고 실패하면 다시 시도 버튼을 띄워줘

20년차 메모"저장됨"만 그리고 "저장 실패"와 "오프라인이라 대기 중"을 안 그리면, 사용자는 날아간 글을 모르고 창을 닫습니다. 실패 상태는 눈에 띄게 하고, 저장 안 된 변경이 있을 때 탭을 닫으려 하면 경고하세요. 입력할 때마다 저장 요청을 보내지 말고 멈춘 뒤 잠시 기다려 보내도록(디바운스) 개발자와 정하세요.

03

드래그 핸들 Drag handle · Grip

항목 옆에 붙은 점 여섯 개(⋮⋮) 모양의 손잡이로, "여기를 잡고 끌면 순서가 바뀐다"는 표시입니다. 항목 전체를 끌 수 있게 하는 것과 달리, 잡는 자리를 손잡이 하나로 정해 줍니다.

언제 쓰나할 일 순서, 메뉴 순서, 즐겨찾기 정렬처럼 사용자가 직접 순서를 정하는 목록.

AI에게 이렇게할 일 목록 항목 왼쪽에 드래그 핸들을 두고, 핸들을 끌어 순서를 바꾸게 하고, 끄는 동안 놓을 자리를 선으로 표시해줘

20년차 메모끌기만 되는 정렬은 키보드와 스크린리더 사용자를 완전히 막습니다. "위로 / 아래로" 버튼이나 키보드 대체 조작을 반드시 같이 주세요. 터치에서는 목록 스크롤과 끌기가 충돌하니 핸들 영역을 따로 두는 게 해법이고, 핸들 크기는 손가락 기준 44pt를 지켜야 합니다.

04

구분선 Divider

내용을 나누는 얇은 선. 가로선은 목록 항목 사이, 가운데 글자가 낀 선("또는")은 두 선택지 사이, 세로선은 나란한 버튼 사이에 씁니다. 여백으로도 나눌 수 있는 것을 선으로 한 번 더 강조하는 장치입니다.

언제 쓰나설정 목록의 그룹 나누기, 로그인 화면의 "또는 소셜 로그인", 하단 버튼 줄 사이.

AI에게 이렇게설정 항목 그룹 사이에는 연한 회색 1px 구분선을 넣고, 소셜 로그인 위에는 가운데 "또는" 글자가 있는 구분선을 넣어줘

20년차 메모선이 너무 많으면 화면이 감옥처럼 보입니다. 먼저 간격과 배경색 차이로 묶고, 그래도 구분이 안 될 때만 선을 쓰세요. 선 색은 배경과 대비가 너무 약하면 일부 화면에서 안 보이지만, 선이 의미 있는 정보를 전달하는 게 아니므로 스크린리더에서는 장식(role="presentation")으로 숨겨도 됩니다.

05

미니 플레이어 Mini player · PiP

다른 화면을 보는 동안에도 재생 중인 음악·영상을 작게 줄여 붙여 두는 것. 앱 안의 하단 막대를 미니 플레이어, 다른 앱 위에까지 떠다니는 작은 영상 창을 PiP(Picture in Picture, 화면 속 화면)라고 부릅니다.

언제 쓰나음악·팟캐스트·영상 앱에서 재생을 유지한 채 다른 목록을 둘러볼 때.

AI에게 이렇게재생 중에 다른 화면으로 가면 하단에 미니 플레이어를 고정하고, 눌러서 전체 플레이어로 확장되게 하고 재생과 정지 버튼을 넣어줘

20년차 메모미니 플레이어가 탭바 위에 겹쳐 쌓이는 높이를 계산하지 않으면 목록의 마지막 줄이 가려집니다. 하단 여백을 그만큼 늘리세요. 닫는 방법(옆으로 밀기, X 버튼)이 없으면 한 번 틀면 영원히 붙어 있습니다. PiP는 브라우저·기기마다 지원이 달라 웹에서는 가능한지 먼저 확인해야 합니다.

06

지도 핀과 클러스터 Map pin · Cluster

지도 위의 위치를 가리키는 물방울 모양이 핀(pin)이고, 가까이 모인 핀 여러 개를 숫자 원 하나로 묶은 것이 클러스터(cluster)입니다. 지도를 확대하면 숫자 원이 풀려서 개별 핀이 됩니다.

언제 쓰나맛집·숙소·매장처럼 한 지도에 장소가 수십 개 이상 찍히는 화면.

AI에게 이렇게지도의 매장 핀이 가까이 모이면 숫자가 적힌 클러스터로 묶고, 클러스터를 누르면 그 영역으로 확대되며 핀이 풀리게 해줘

20년차 메모핀을 누르면 정보 카드가 열리는데, 카드가 지도 위의 다른 핀을 덮거나 지도 조작과 충돌하는 경우가 많습니다. 선택된 핀은 색과 크기로 구분하고, 빈 지역·위치 권한 거부 상태도 그려야 합니다. 핀 색만으로 종류를 나누면 접근성이 떨어지니 아이콘 모양을 함께 쓰세요.

07

고정 열 Frozen · Sticky column

표를 옆으로 스크롤해도 첫 열(보통 이름)만 제자리에 붙어 있는 것. 스프레드시트의 "열 고정"이 같은 기능이고, 같은 방식으로 맨 윗줄(제목 줄)을 고정하는 것은 고정 행입니다. 왼쪽 표를 가로로 밀어 보세요.

언제 쓰나열이 많아 가로 스크롤이 생기는 표에서 "이 값이 누구 것인지"를 계속 보여줘야 할 때.

AI에게 이렇게열이 많은 표는 가로 스크롤하되 첫 번째 이름 열과 제목 줄은 고정 열과 고정 행으로 붙여줘

20년차 메모고정 열의 배경이 투명하면 스크롤되는 글자가 비쳐서 글자가 겹쳐 보입니다. 반드시 불투명한 배경과 오른쪽 그림자를 주세요. 고정하는 열이 3개를 넘으면 스크롤 영역이 거의 안 남으니 최대 1~2개로 제한하고, 모바일에서는 표 대신 카드 목록으로 바꾸는 것도 고려하세요.

08

가상 스크롤 Virtual scroll · Windowing

수천~수만 줄 목록에서 화면에 보이는 몇 줄만 실제로 그리고 스크롤에 맞춰 내용을 바꿔 끼우는 기법. 사용자에게는 긴 목록이 다 있는 것처럼 보이지만 브라우저는 몇 줄만 다룹니다. 아래쪽에서 데이터를 조금씩 더 불러오는 무한 스크롤과는 다른 이야기입니다.

언제 쓰나채팅 기록, 로그, 대용량 표처럼 목록이 수천 줄을 넘어 화면이 버벅거릴 때.

AI에게 이렇게1만 줄짜리 로그 목록이 느리니까 가상 스크롤로 바꿔서 보이는 줄만 렌더링하게 해줘

20년차 메모가상 스크롤을 쓰면 브라우저의 "페이지 내 검색"(Ctrl+F)이 화면 밖 줄을 못 찾고, 줄 높이가 제각각이면 스크롤바가 튑니다. 디자인에서는 줄 높이를 가능한 한 고정하세요. 성능 문제가 실제로 없는 200줄 목록에는 쓰지 마세요. 복잡도만 늘어납니다.

09

레이지 로딩 Lazy loading

이미지나 화면 조각을 처음부터 다 받지 않고, 스크롤해서 화면에 가까워질 때 받아오는 방식. 첫 화면이 빨리 뜹니다. 회색 자리표시자를 먼저 보여주는 것은 스켈레톤이고, 가상 스크롤은 이미 받은 데이터를 적게 그리는 방식이라 서로 다릅니다.

언제 쓰나사진이 많은 피드, 긴 상품 목록, 페이지 아래쪽의 무거운 영역.

AI에게 이렇게스크롤 아래쪽의 이미지는 레이지 로딩으로 화면에 들어오기 직전에 불러오고, 이미지 자리의 가로세로 비율은 미리 잡아줘

20년차 메모이미지 자리 크기를 안 잡아 두면 로딩될 때마다 글이 아래로 밀립니다. 그리고 첫 화면에 보이는 대표 이미지에 레이지 로딩을 걸면 오히려 가장 중요한 사진이 늦게 뜹니다. 첫 화면 위쪽은 즉시 로딩, 아래쪽만 지연 로딩이 원칙입니다.

10

딥링크 Deep link

앱이나 사이트의 첫 화면이 아니라 특정 화면(예: 이 상품의 상세)으로 곧장 연결되는 링크. 앱에서는 myapp://product/123처럼 앱 전용 주소를 쓰기도 합니다. 홈 화면만 열어 주는 일반 링크와 구분됩니다.

언제 쓰나푸시 알림, 문자·카카오톡 공유, 광고, QR코드에서 사용자를 원하는 화면으로 바로 보낼 때.

AI에게 이렇게공유한 상품 링크를 누르면 앱이 설치돼 있을 때 상품 상세 화면으로 딥링크로 바로 열리고, 설치 전이면 스토어로 보내줘

20년차 메모딥링크 설계는 "그 링크를 눌렀는데 로그인이 필요하거나 앱이 없으면 어디로 가나"가 전부입니다. 로그인 후 원래 가려던 화면으로 돌아오는 흐름과, 삭제된 상품 링크의 빈 화면을 반드시 그리세요. 개발에서는 iOS 유니버설 링크, 안드로이드 앱 링크 설정이 따로라 일정이 걸린다는 점도 알아 두세요.

11

푸시 알림 vs 인앱 메시지 Push notification vs In-app message

앱이 꺼져 있어도 폰 잠금 화면과 알림창에 뜨면 푸시 알림, 사용자가 앱을 쓰고 있을 때 앱 화면 안에 뜨면 인앱 메시지입니다. 푸시는 사용자의 허락(권한)이 있어야 보낼 수 있고, 인앱은 앱을 연 사람에게만 보입니다.

이렇게 구분앱을 안 쓰는 사람을 다시 불러야 하면 푸시, 지금 쓰는 사람에게 안내하거나 유도하면 인앱 메시지.

AI에게 이렇게쿠폰 발급은 푸시 알림으로 보내고, 앱을 열었을 때 아직 안 쓴 쿠폰이 있으면 상단 인앱 메시지로 한 번 더 알려줘

20년차 메모푸시 권한 요청을 앱을 처음 열자마자 띄우면 거절당하고, iOS에서는 한 번 거절하면 시스템 설정에서만 다시 켤 수 있습니다. 가치를 보여준 뒤 묻고, 거절한 사람에게는 인앱 메시지로 대신 알리는 경로를 설계하세요. 푸시 문구는 잠금 화면에서 잘리므로 앞 30자 안에 핵심을 넣어야 합니다.

12

알림 센터 Notification center

그동안 받은 알림을 한곳에 모아 다시 볼 수 있게 한 목록. 종 아이콘 위의 숫자 배지로 안 읽은 개수를 알리고, 누르면 목록이 열립니다. 토스트처럼 잠깐 떴다 사라지는 알림과 달리 기록이 남습니다.

멘탈 모델 Mental model

사용자가 "이건 이렇게 돌아가겠지" 하고 머릿속에 갖고 있는 작동 방식에 대한 그림. 실제 시스템 구조와 다를 수 있고, 둘이 어긋날 때 "왜 이렇게 되지?"라는 혼란과 사고가 생깁니다. 디자이너가 만든 개념 모델과도 구분됩니다.

전환율 Conversion rate

방문한 사람 중 우리가 바라는 행동(구매, 가입, 신청)을 실제로 한 사람의 비율. "전환수 ÷ 전체 방문자 수"로 계산합니다. 단계별로 나눠 보면 사람들이 어느 단계에서 빠지는지 보이고, 이를 깔때기 모양이라 하여 퍼널(funnel)이라 부릅니다.

이럴 때 쓴다화면 개선이 실제로 효과가 있었는지 전후를 비교하거나, 퍼널에서 가장 크게 새는 단계를 찾을 때.

AI에게 이렇게방문, 장바구니, 결제 단계별 전환율을 퍼널 차트로 보여주고 가장 많이 이탈하는 단계를 표시해줘

20년차 메모분모를 무엇으로 잡느냐가 전부입니다. 전체 방문자인지, 상품을 본 사람인지, 신규 방문자만인지 합의하지 않으면 팀마다 다른 숫자를 말합니다. 전환율이 올라도 매출이 안 오르는 경우(가격 인하, 저품질 가입)가 있으니 "무엇을 전환으로 칠 것인가"를 하나 정하고 보조 지표와 함께 보세요.

이탈률 vs 종료율 Bounce rate vs Exit rate

방문의 첫 페이지에서 다른 행동 없이 곧바로 떠난 비율이 이탈률(Bounce rate), 방문 중 어느 페이지든 마지막으로 보고 떠난 비율이 종료율(Exit rate)입니다. 이탈률은 "처음 만난 페이지의 실망", 종료율은 "그 페이지가 끝점이 된 비율"입니다. 분석 도구마다 이탈의 정의가 조금씩 다릅니다.

이렇게 구분첫 페이지에서 한 번도 안 넘어가고 나가면 이탈, 여러 페이지를 본 뒤 그 페이지에서 끝나면 종료. 결제 완료 페이지의 높은 종료율은 정상입니다.

AI에게 이렇게랜딩 페이지별 이탈률과 결제 단계 페이지별 종료율을 따로 계산하는 분석 쿼리를 만들어줘

20년차 메모이탈률이 높다고 무조건 나쁜 페이지가 아닙니다. 전화번호 하나 찾아서 떠나는 안내 페이지는 목적을 달성한 이탈입니다. 반대로 결제 단계 중간의 종료율은 위험 신호입니다. 지표를 그대로 보지 말고 "이 페이지는 사용자가 거기서 끝내도 되는 페이지인가"를 먼저 물으세요.

처음 쓴 사람이 며칠·몇 주 뒤에도 다시 돌아오는 비율. 같은 시기에 가입한 사람끼리 묶은 집단을 코호트(cohort)라 하고, 가입 월별로 재방문율을 늘어놓은 위 표를 코호트 표라 부릅니다. 진할수록 많이 남은 칸입니다(숫자는 가상).

이럴 때 쓴다"가입자는 늘었는데 쓰는 사람이 안 늘어난다"는 의심이 들 때, 온보딩이나 기능을 바꾼 뒤 효과를 코호트별로 비교할 때.

AI에게 이렇게가입 월별 코호트로 1일, 7일, 30일 리텐션을 계산해 색이 진할수록 높은 히트맵 표로 보여줘

20년차 메모"다시 방문"의 기준을 정하지 않으면 숫자가 무의미합니다. 앱을 열기만 해도 되는지, 핵심 행동을 해야 하는지 정하세요. 가장 최근 코호트는 아직 시간이 안 지나 칸이 비어 있는데, 그걸 0으로 보고 개선이 실패했다고 판단하는 실수가 흔합니다. 전체 평균 하나로 보면 좋은 코호트와 나쁜 코호트가 섞여 안 보입니다.

만족도 지표 CSAT · SUS

사용자의 만족을 숫자로 재는 설문 방식. CSAT(고객 만족도)는 "방금 경험이 만족스러웠나요?"를 1~5점으로 한 번 묻는 것이고, SUS(시스템 사용성 척도)는 10개 문항을 1~5점으로 답하게 해 사용성을 0~100점으로 환산하는 표준 설문입니다.

이럴 때 쓴다상담 종료나 구매 직후처럼 특정 순간의 만족을 가볍게 모을 때는 CSAT, 서비스 전체의 사용성을 개선 전후로 비교할 때는 SUS.

AI에게 이렇게상담이 끝나면 1~5점 CSAT 설문을 한 문항 띄우고, 낮은 점수를 준 사람에게만 이유를 묻는 주관식 칸을 보여줘

20년차 메모CSAT는 묻는 시점과 문구에 따라 숫자가 크게 흔들리니, 기간을 넘나드는 비교는 문구를 고정한 상태에서만 하세요. SUS 점수 하나로 "좋다/나쁘다"를 말하기보다 개선 전후나 경쟁 서비스와의 상대 비교에 쓰는 게 안전합니다. 설문 창이 작업을 가로막으면 점수가 아니라 짜증만 얻습니다.

과업 성공률 Task success rate

사용성 테스트에서 "이 일을 해 보세요"라고 시킨 과업을 성공적으로 끝낸 참가자의 비율. "성공 인원 ÷ 전체 참가자"로 계산하며, 도움을 받아 겨우 끝낸 경우를 성공으로 칠지 미리 정합니다. 만족도처럼 마음이 아니라 실제 행동의 결과를 잽니다.

이럴 때 쓴다가입·결제·환불처럼 핵심 과업을 사용자가 정말 끝낼 수 있는지 확인하고, 개선 전후를 비교할 때.

AI에게 이렇게사용성 테스트 결과표에서 과업별 성공, 도움받아 성공, 실패 인원을 세어 과업 성공률과 실패 원인 요약을 정리해줘

20년차 메모참가자 5명의 "80%"는 통계가 아니라 "4명이 됐고 1명이 막혔다"는 관찰입니다. 퍼센트보다 막힌 사람이 어디서 왜 멈췄는지를 기록하세요. 성공의 정의(정해진 시간 안에? 도움 없이?)를 테스트 전에 적어 두지 않으면 보고서마다 숫자가 달라지고, 쉬운 과업만 골라 성공률을 높이는 실수도 흔합니다.
