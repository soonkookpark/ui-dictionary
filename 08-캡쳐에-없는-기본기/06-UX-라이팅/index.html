01

마이크로카피 Microcopy

버튼, 입력칸 안내, 오류, 빈 화면처럼 화면 속에서 사용자의 행동을 돕는 아주 짧은 글. 광고 문구나 기사 같은 긴 글과 구분해서 부르는 이름입니다. UX 라이팅의 가장 작은 단위입니다.

언제 쓰나사용자가 멈칫하거나 망설이는 모든 자리. 가입, 결제, 삭제, 권한 요청 직전.

AI에게 이렇게가입 화면의 모든 마이크로카피를 사용자가 바로 이해할 쉬운 해요체로 다시 써줘

20년차 메모시안에는 "버튼", "설명 문구"라고만 적히고 실제 문장은 개발자가 채우는 일이 많습니다. 그러면 길이도 말투도 제각각이 됩니다. 시안 단계에서 실제 문장을 넣으세요. 한국어는 영어보다 길어서 줄 바꿈 위치도 그때 정해집니다.

나쁜 예

삭제할까요?

vs
좋은 예

삭제할까요?

02

버튼 문구 Button label

버튼 글은 "확인"처럼 막연한 말 대신, 누르면 일어날 일을 동사로 끝내는 말로 씁니다. 글만 읽어도 다음에 무슨 일이 생기는지 알 수 있어야 합니다.

언제 쓰나저장하기, 삭제하기, 결제하기, 초대 보내기처럼 모든 버튼, 특히 되돌리기 어려운 동작.

AI에게 이렇게"확인", "예", "아니오" 같은 버튼 문구를 모두 누르면 일어날 일을 말하는 동사형으로 바꿔줘

20년차 메모"확인/취소"는 질문이 "~하시겠습니까?"일 때 확인이 무엇에 대한 확인인지 헷갈려 오터치가 잘 납니다. 버튼 글은 길어도 3~4어절 안으로 줄이고, 화면 읽기 프로그램은 버튼 글만 따로 읽으니 "여기를 누르세요" 같은 말은 쓰지 마세요.

나쁜 예오류가 발생했습니다. (E-4012)
vs
좋은 예비밀번호가 맞지 않아요. 다시 입력하거나 비밀번호 찾기를 눌러 주세요.

03

오류 메시지 Error message

좋은 오류 메시지는 세 가지를 담습니다. 무슨 일이 일어났는지, 왜 그런지, 이제 어떻게 하면 되는지. 사용자를 탓하는 말투는 피합니다.

언제 쓰나입력 검증 실패, 네트워크 끊김, 결제 거절, 권한 없음 등 일이 잘못된 모든 순간.

AI에게 이렇게모든 오류 메시지를 무슨 일, 왜, 어떻게 하면 되는지 세 요소로 다시 써주고 내부 오류 코드는 화면에서 빼줘

20년차 메모오류 코드는 사용자가 아니라 고객센터에 필요한 정보이니 작은 글씨로 맨 아래에 두세요. 입력칸 오류는 칸 바로 아래에, 붉은색만이 아니라 글로도 알려야 색을 구분하지 못하는 사람도 알아봅니다. 그리고 "~하지 못했습니다"만 반복하는 서버 기본 문구가 그대로 노출되지 않는지 꼭 확인하세요.

나쁜 예

데이터 없음

vs
좋은 예

아직 저장한 글이 없어요

마음에 드는 글을 저장하면 여기에 모여요.

04

빈 화면 문구 Empty state copy

목록이나 검색 결과에 보여줄 것이 없을 때의 글. "없음"이라고 알리는 데서 끝내지 않고, 왜 비었는지와 다음에 할 일을 알려 주는 기회로 씁니다.

언제 쓰나처음 가입한 직후, 알림이 없을 때, 검색 결과가 0건일 때, 필터를 걸어 모두 가려졌을 때.

AI에게 이렇게찜 목록이 비었을 때 보여줄 빈 화면 문구를 제목, 한 줄 설명, 다음 행동 버튼 세 줄로 써줘

20년차 메모"처음 비어 있음", "검색 결과 없음", "필터 때문에 비어 있음", "불러오기 실패"는 서로 다른 상태인데 같은 문구를 쓰는 경우가 많습니다. 특히 불러오기 실패를 "내용이 없어요"로 보여주면 사용자가 자기 데이터가 사라진 줄 압니다.

나쁜 예

확인

정말로 하시겠습니까?

vs
좋은 예

작성 중인 글을 지울까요?

지우면 되돌릴 수 없어요.

05

확인 대화상자 문구 Confirmation dialog copy

제목은 무엇을 하려는지 묻는 질문으로, 버튼은 그 질문에 대한 행동으로 씁니다. 제목과 버튼만 읽어도 상황이 이해되어야 합니다.

언제 쓰나삭제, 나가기, 결제, 로그아웃처럼 되돌리기 어렵거나 작성 중인 내용을 잃을 수 있는 순간.

AI에게 이렇게모든 확인 대화상자의 제목은 질문형으로, 버튼은 "예/아니오" 대신 행동 동사로 바꿔줘

20년차 메모"예/아니오"는 질문이 부정문이면("저장하지 않고 나갈까요?") 어느 쪽이 안전한지 순간 헷갈립니다. 안전한 선택은 왼쪽이나 기본 강조에, 위험한 행동은 붉은 글자로 두는 식으로 규칙을 정하세요. 모든 일에 확인창을 띄우면 아무도 읽지 않게 되니, 되돌릴 수 있는 일은 "실행 취소"로 처리하는 편이 낫습니다.

나쁜 예
vs
좋은 예
두 칸에 글자를 입력해 보세요. 왼쪽은 무슨 칸인지 사라집니다

06

플레이스홀더 문구 Placeholder text

입력칸 안에 옅게 보이다가 입력하면 사라지는 안내 글. 칸의 이름(라벨)을 대신하는 것이 아니라, 입력 예시를 보여주는 보조 수단입니다.

언제 쓰나형식이 헷갈리는 칸의 예시(전화번호 형식, 날짜 형식), 검색창의 "무엇을 찾나요?" 같은 짧은 힌트.

AI에게 이렇게모든 입력칸에 항상 보이는 라벨을 달고, 플레이스홀더에는 입력 예시만 넣어줘

20년차 메모플레이스홀더만 있는 폼은 입력을 시작하는 순간 질문이 사라져서, 긴 폼에서 앞 칸을 다시 확인하려면 지워야 합니다. 옅은 회색이라 명도 대비가 4.5:1에 못 미치는 경우도 많아 중요한 정보를 거기에 넣으면 안 읽힙니다. 검색창처럼 목적이 분명한 한 칸 정도만 예외입니다.

성공
저장했어요. 이제 다른 기기에서도 볼 수 있어요.
오류
저장하지 못했어요. 연결을 확인하고 다시 눌러 주세요.
안내
사진은 최대 10장까지 올릴 수 있어요.
말투는 같고, 상황마다 온도만 다릅니다

07

보이스와 톤 Voice & Tone

보이스는 서비스가 늘 가진 성격과 말투(친근하다, 정중하다), 톤은 상황에 따라 바뀌는 온도(축하할 때 밝게, 오류일 때 차분하게)입니다. 사람으로 치면 목소리는 같고 기분이 다른 것입니다.

언제 쓰나서비스 전체의 글 규칙을 정할 때, 여러 사람이 글을 쓰는 팀에서 문체 가이드를 만들 때.

AI에게 이렇게우리 서비스의 보이스를 "친근하지만 가볍지 않은 해요체"로 정하고, 성공·오류·안내 상황별 톤 예시를 써줘

20년차 메모가장 흔한 실패는 오류 상황에서도 평소의 장난스러운 톤을 유지하는 것입니다. 사용자가 결제에 실패했는데 귀여운 농담이 나오면 화가 납니다. 밝은 톤은 사용자가 이기고 있을 때만, 문제가 생겼을 때는 차분하고 구체적으로 쓰세요.

저장하였습니다.
다음으로 가요
사진을 선택하세요.
완료됨
vs
좋은 예
저장했어요.
다음으로 가요
사진을 골라 주세요.
완료했어요

08

문체 일관성 Consistent speech style

한 서비스 안에서 해요체(~해요)와 합니다체(~합니다), 평서문과 명사형(~됨)을 섞지 않는 것. 한국어는 어미만 바뀌어도 서비스의 인상이 달라집니다.

언제 쓰나화면 글을 쓰기 전에 어미 규칙을 하나 정하고, 새 화면이 추가될 때마다 같은 규칙으로 점검할 때.

AI에게 이렇게앱 전체 문구의 문체 일관성을 점검해서 합니다체와 해요체가 섞인 곳을 해요체로 통일해줘

20년차 메모섞이는 지점은 대개 개발자가 급히 넣은 오류 문구와 서버가 내려주는 기본 문구입니다. 해요체인지 합니다체인지는 금융·의료처럼 신뢰가 중요하면 합니다체, 일상 앱이면 해요체가 보통이지만, 정답이 아니라 정해서 지키는 것이 핵심입니다. 푸시 알림과 이메일까지 같은 문체인지 확인하세요.

나쁜 예
2026-11-23 14:03:11
1200
1 comment(s)
2026/11/20 ~ 11/23
vs
좋은 예
3분 전
1,200원
댓글 1개
11월 20일 ~ 23일

09

숫자·날짜 표기 Number & date format

컴퓨터가 쓰는 형식 그대로가 아니라 사람이 읽는 형식으로 바꿔 보여주는 것. 천 단위 쉼표, 단위, "3분 전" 같은 상대 시간이 대표적입니다.

언제 쓰나가격, 수량, 작성 시간, 기간, 거리, 파일 크기처럼 숫자가 나오는 모든 자리.

AI에게 이렇게가격은 천 단위 쉼표와 "원", 작성 시간은 상대 시간으로 보여주고 일주일이 지나면 날짜로 바꿔줘

20년차 메모"3분 전"은 일주일쯤 지나면 오히려 불편해서 날짜로 바꾸는 기준을 정해야 합니다. 개수는 "1개"와 "2개"를 같은 칸에 넣을 때 폭이 바뀌어 흔들리지 않는지, 0일 때와 999+처럼 아주 클 때는 어떻게 보이는지까지 정해 두세요. 해외 서비스라면 날짜 순서와 통화 표기가 나라마다 다릅니다.

나쁜 예
메뉴장바구니
버튼카트에 담기
알림쇼핑백에 추가됨
vs
좋은 예
메뉴장바구니
버튼장바구니에 담기
알림장바구니에 담았어요

10

용어 일관성 Terminology consistency

같은 것은 어디서나 같은 말로, 다른 것은 다른 말로 부르는 것. 화면마다 이름이 다르면 사용자는 서로 다른 기능이라고 생각합니다.

언제 쓰나서비스 핵심 개념(장바구니, 찜, 보관함)과 화면·메뉴·알림·고객센터 글을 맞출 때.

AI에게 이렇게앱 전체에서 "장바구니"를 가리키는 표현을 찾아 용어 일관성 있게 하나로 통일하고 용어집으로 정리해줘

20년차 메모코드 안의 이름(cart, basket)과 화면의 이름이 달라서 개발자와 디자이너가 서로 다른 것을 이야기하는 일이 많습니다. 용어집을 한 장 만들어 화면 글과 코드 이름을 같은 줄에 적어 두세요. 반대 방향 사고도 있습니다. 서로 다른 기능(삭제와 보관)을 같은 말로 부르는 경우입니다.

나쁜 예

인증 토큰이 만료되었습니다

세션을 갱신하세요.

vs
좋은 예

오랫동안 쓰지 않아 로그아웃됐어요

안전을 위해서예요. 다시 로그인해 주세요.

11

사용자 말로 쓰기 Plain language

토큰, 세션, 파라미터, 인스턴스 같은 시스템 안쪽의 말 대신 사용자가 일상에서 쓰는 말로 쓰는 것. 기술 용어는 만든 사람에게만 쉽습니다.

언제 쓰나오류, 권한 요청, 설정 화면처럼 개발자가 쓴 문장이 그대로 노출되기 쉬운 곳.

AI에게 이렇게화면에 나오는 문구에서 토큰, 세션, 인증 같은 시스템 용어를 찾아 사용자 말로 풀어 써줘

20년차 메모쉬운 말은 짧은 말이 아니라 사용자가 쓰는 말입니다. 사용자가 "구독 해지"라고 검색하는데 화면에는 "멤버십 종료"라고 쓰면 못 찾습니다. 고객센터 문의 내용과 앱 스토어 후기에서 실제 쓰는 단어를 모으면 가장 빠릅니다.
